# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## What This Project Is

moldordie is a fork of [cookiecutter-django](https://github.com/cookiecutter/cookiecutter-django), a **Cookiecutter template** that generates production-ready Django projects. It is NOT a Django application itself — it's a Jinja2-templated project scaffold. The generated project lives inside `{{cookiecutter.project_slug}}/` and gets processed by Cookiecutter when users run the generator.

## Commands

### Install dependencies

```bash
uv sync --locked
```

### Run tests

```bash
# Full test suite (parallel, via tox)
uv run tox run -e py

# Direct pytest (parallel)
uv run pytest -n auto tests

# Single test
uv run pytest tests/test_cookiecutter_generation.py -k "test_name"

# Run with auto-fixable style checks enabled
AUTOFIXABLE_STYLES=1 uv run pytest -n auto tests

# Only the auto-fixable style checks, as CI's own job runs them
AUTOFIXABLE_STYLES=1 uv run pytest -n auto tests -m auto_fixable
```

### Linting and formatting

```bash
# Run all pre-commit hooks
uv run pre-commit run --all-files

# Ruff only
uv run ruff check --fix
uv run ruff format
```

### Integration tests (require Docker or PostgreSQL+Redis)

```bash
# Docker-based
sh tests/test_docker.sh                          # defaults
sh tests/test_docker.sh use_celery=y rest_api=DRF  # with options

# Bare metal (needs PostgreSQL and Redis running)
sh tests/test_bare.sh
sh tests/test_bare.sh use_celery=y rest_api=DRF
```

### Generate a project locally for debugging

```bash
uv run cookiecutter . --no-input --output-dir=/tmp/debug
```

### Compare what two revisions generate

```bash
# Every supported combination baked from main and from the working tree, drawn values masked
uv run scripts/compare_generated.py
# Another base, and an extra row for a fork no supported combination reaches
uv run scripts/compare_generated.py --base HEAD~1 "use_docker=y postgresql_version=14"
```

About a minute; not part of the suite. This is how a refactor of the template is shown to leave the generated projects alone: it proves equality for the rows it baked and nothing about a row it did not bake. Put the command and its result in the pull request.

## Architecture

### Template Generation Flow

1. User runs `cookiecutter` (2.2.0 or later) — prompted with options from `cookiecutter.json`
2. `hooks/pre_gen_project.py` normalises the answers (trims the domain and email, lowercases the flags) and binds the derived answers (`headless`, `service_tokens`, booleans computed by `derived_answers` in `local_extensions.py`; `docs/adr/0022`), then validates input (project_slug format, control characters, the domain name's characters, conflicting options)
3. Jinja2 renders all files under `{{cookiecutter.project_slug}}/` with user choices, with `templates/` at the repository root on the loader's path for `include` and `import` and never rendered as output (the shared source, a term in `CONTEXT.md`); free-text answers pass through the escaping filter of each file's syntax (`local_extensions.py`, terms in `CONTEXT.md`)
4. `hooks/post_gen_project.py` receives the answers as JSON, prunes the files the chosen options do not need and generates random secrets

### Key Files

- **`cookiecutter.json`** — All template variables and their choices (project name, Docker, Celery, cloud provider, REST API, etc.)
- **`hooks/pre_gen_project.py`** — Pre-generation validation: project slug, control characters, the domain name's characters, conflicting options (uses Jinja2 syntax at the top for context manipulation: the normalisation, then `cookiecutter.update(derived_answers(cookiecutter))`, so every template and the post-generation hook read the derived answers by name)
- **`hooks/post_gen_project.py`** — Post-generation hook, whose removal rules and secrets table read the derived answers from the context (`c["headless"]`, `c["service_tokens"]`; `docs/adr/0022`): `DEPLOYED_ENVIRONMENTS`, named once in promotion order, with `env_file` and `env_files` deriving an environment's env-file paths; `SECRETS`, the table of secrets, in which a value each deployed environment draws for itself is declared once through `per_deployed_environment` and expanded to one row per environment, and `fill_secrets`, which draws and writes them; `write_example_dotenv`, which derives `.env.example` from the production env files and must run before them (`docs/adr/0014`); `REMOVALS`, the table of removal rules, and `prune`, which applies them plus the Channels cleanup; `AGENT_FILES` and `place_agent_guide`, which move the agent guide to the file the chosen coding agent reads, after pruning (`docs/adr/0015`; terms in `CONTEXT.md`)
- **`local_extensions.py`** — The option catalogue (`OPTIONS`, `option_names`, which takes one kind or several so the agent guide's table of choices renders in declaration order; the kinds are defined under Option in `CONTEXT.md`), read from `cookiecutter.json`; `derived_answers`, the one pure function that computes the derived answers (a term in `CONTEXT.md`) from the answers, tested against a hand-written truth table in `tests/test_derived_answers.py`; and the `string_escape` Jinja filter that a free-text answer passes through where it lands inside a Python, TOML, YAML or gettext string (in HTML it passes through Jinja's `e`). All three reach Cookiecutter through `_extensions` in `cookiecutter.json`; the hooks run as standalone scripts and cannot import the catalogue, so they read it through the `option_names` and `derived_answers` Jinja globals
- **`{{cookiecutter.project_slug}}/`** — The template directory; files here use Jinja2 conditionals (`{% if cookiecutter.use_celery == 'y' %}`) to include/exclude content
- **`templates/`** — The shared source (`docs/adr/0023`): `deployed/django.env` and `deployed/postgres.env` (a deployed environment's env files), `deployed/compose.yml` (its Compose file, the name its only input) and `deployed/routers.yml` (its Traefik routers, with production's `www` arm), each written once, and `deployed/environments`, the table of what an environment differs in (its host, whether the apex answers as `www`), keyed by name. The twelve files under `{{cookiecutter.project_slug}}/.envs/.{dev,test,production}/`, `docker-compose.{dev,test,production}.yml` and `compose/production/traefik/dynamic/{dev,test,production}.yml` are two-line stubs that set `environment` and include the source for their kind; a deployment variable, service, volume or router is added to the source, never to a stub. Jinja, so excluded from pre-commit and ruff like the project template

### Test Structure

- **`tests/test_cookiecutter_generation.py`** — Main test file. Uses `pytest-cookies` to bake the template with `SUPPORTED_COMBINATIONS`: the defaults, one row per choice of every list and flag option in the catalogue, and the hand-written `PAIRED_COMBINATIONS`, deduplicated so each project bakes once. Between them the rows must keep every path a removal rule lists: `test_every_removable_path_is_baked` needs no bake, and names an unreached path with the smallest supported row that would keep it (file-level only, `docs/adr/0021`). The `bake` fixture generates the project its answers select and returns the reader, once per set of answers and test process: every test that bakes the same answers gets the same tree, so a tool that rewrites files (django-upgrade) runs on a copy and ruff runs without its cache (`docs/adr/0002`). Under xdist a process is a worker, so the tests parametrized over the combinations carry their combination as an `xdist_group` and `--dist loadgroup`, the default in `addopts`, runs each group on one worker. A test expecting the hook to refuse bakes through `cookies`. Verifies: no Jinja syntax left in output, generated code passes linting, correct files present/absent, no file citing a path the combination's answers removed (`test_no_file_cites_a_path_its_answers_removed`, the removed paths derived from the rules; `ALLOWED_CITATIONS` is hand-written, a reason each), the agent guide placed where its agent reads it with its choices table and its layout table checked against the tree, the stylesheet's wiring (the Tailwind settings in `base.py` alone, the source stylesheet outside the static directories, the built one never generated, the image build and the watcher service; nothing here runs the Tailwind CLI), the metrics wiring (the app, the middleware pair, the instrumented backends, the endpoint and the multiprocess lifecycle; nothing here scrapes), the telemetry wiring (the app, the settings, the entry point of each serving process and the local collector; nothing here exports), and, with `AUTOFIXABLE_STYLES=1`, that `ruff format`, djlint's formatter and `django-upgrade` would change nothing (the `auto_fixable` marker; CI runs just those in its own job).
- **`tests/answers.py`** and **`tests/removal_coverage.py`** — Shared support that asserts nothing, like the reader. `complete_answers` is the one place a row becomes the answers it generates from (the catalogue's defaults, then each layer of answers in turn: for a CI row its script's own, then the row's; then the derived answers, as the pre-generation hook binds them); the generation tests, the hook tests' `context_of` and `tests/test_ci_rows.py` go through it. `parse_answers` and `unknown_answers` read a row written as `name=value` words and check it against the catalogue, for the CI rows and for the extra rows of `scripts/compare_generated.py`. `paths_kept(rules, rows)` says for every path the rules list whether some row keeps it, `removed_paths` what the rules delete for one set of answers, `coverage_gaps` weighs the result against hand-written exemptions, and `fewest_answers_keeping` finds the missing row for a failure message; they are handed the rules and a way to complete a row, and import nothing from the hook
- **`tests/citations.py`** — The citation check, asserting nothing: `citations(files, removed, allowed, package=)` returns which text files of a generated project name a path its answers removed, and which allowances covered nothing. A directory is matched with its trailing slash (its bare name may be prose), a file by its whole name bounded by what cannot continue a path, and a path inside the package also relative to it. `tests/test_citations.py` tests it on hand-written files
- **`tests/test_derived_answers.py`** — `derived_answers` against a hand-written truth table over all 27 combinations of the identity provider, the REST API and observability, stated as the sets where each name holds; the global reaching a Cookiecutter environment; and the guard against drift back, `test_no_template_re_derives_a_derived_answer`, which scans the project template and the shared source for a tag that combines the identity provider with the REST API or observability, or binds `headless` or `service_tokens` to anything but the derived answer
- **`tests/test_answers.py`** and **`tests/test_removal_coverage.py`** — The support above on hand-written input: layers over the defaults, rows read from text; rules, rows, defaults and exemptions written by hand, never the hook's table, because a bug in the computation would make the real checks pass vacuously
- **`tests/generated_project.py`** — The reader (a term in `CONTEXT.md`): `GeneratedProject` locates the files under a generated root and parses the ones with a syntax (`env`, `compose`, `pins`, `settings`); `PythonModule` reads what a Python file binds at module scope from its source, over the subset its docstring lists, and fails explicitly outside it (`docs/adr/0001`). Nothing in it asserts, checks existence or validates the tree
- **`tests/test_generated_project.py`** — The reader on hand-written modules and trees: the forms it resolves, aliasing and mutation, conditional bindings, rejected modules, the `env` reads and the file readers
- **`tests/test_hooks.py`** — Unit tests for the hooks: `fill_secrets` run on hand-written placeholder files through a generator the test controls, with the secrets table checked against the placeholder sites of the template and, for the deployed environments' env files, of the shared source their stubs include (the deployed environments' sites stated once and expanded over the tests' own tuple of them, which is checked against the hook's); `prune` run on a copy of the template tree against hand-written expected removals, and the removal rules checked for consistency over every combination of the answers they read; `place_agent_guide` run on a hand-written guide, with the order it takes in `main` asserted from the hook's source
- **`tests/test_options.py`** — The catalogue: every option's kind against a hand-written mapping (`KINDS`), `option_names` over one kind and over several, the `option_names` global reaching a Cookiecutter environment, and the catalogue's other readers checked against it: the README's example session and the options page
- **`tests/test_ci_rows.py`** — The projects the CI integration jobs generate: each row of `.github/workflows/ci.yml` read with the answers its script passes to Cookiecutter itself (`use_docker`, taken from the script the job's step runs), both checked against the catalogue, and the rows held to the removal rules: `test_every_removable_path_is_generated_by_some_ci_row` fails when no row keeps a listed path, so a row cannot be replaced or narrowed silently; `CI_EXEMPTIONS` is hand-written, a reason per path, and a needless exemption fails (`docs/adr/0021`)
- **`tests/test_local_extensions.py`** — The `string_escape` filter round-tripped through the Python, TOML and YAML parsers, and loaded from `cookiecutter.json`
- **`tests/test_compare_generated.py`** — What `scripts/compare_generated.py` decides, on hand-written input: the extra rows checked against the catalogue, and what it reports for two trees (drawn values masked in the files that hold them and nowhere else, the executable bit, a directory left empty). One test bakes, two rows from the working tree against itself: the masking is complete, and a row the hook refuses is reported, not skipped
- **`tests/test_update_changelog.py`** — The pull request selection and grouping of `scripts/update_changelog.py`, against stand-ins for the pull requests it reads
- **`tests/test_workflows.py`** — This repository's workflows against the files they read: every `.pre-commit-config.yaml` the auto-update workflow parses has to be YAML as it stands, before Cookiecutter renders it
- **`tests/test_bare.sh`** / **`tests/test_docker.sh`** — Integration scripts that generate a project and run its checks: mypy, its test suite, `makemigrations --check`, Django's checks with the local settings and its deployment checks with the production settings (placeholders stand in for the secrets, and `SENTRY_DSN` is empty, as the deployed env files declare it: with `use_sentry=y` the check loads the Sentry settings and starts the SDK without a transport, which shows that the configuration loads and nothing about reporting), `makemessages --all` (that extraction completes and updates the catalogues, nothing about the translations themselves), `tailwind build` from the command line (that the pinned CLI downloads and builds the stylesheet there) and the docs build; the Docker script also checks that the `tailwind` watcher service builds the stylesheet and stays up, that the production image carries the stylesheet and not the CLI, and, where the project has an nginx image (no cloud provider), that it builds, not that nginx serves media. They stay two scripts because their setup differs, an interpreter and OS packages against image builds (`docs/adr/0004`); a new check goes into both by hand, with the settings module explicit

### Generated Project Layout

The generated Django project uses:

- `config/settings/{base,local,test,production}.py` — Split settings with django-environ; importing a settings module has no side effect beyond binding names, so the generated `tests/test_production_settings.py` loads `production.py` under the environment `.envs/.production` declares (`docs/adr/0006`). There is no module per deployment: all three deployed environments run `production.py`, which each of their `.django` files names in `DJANGO_SETTINGS_MODULE` (`docs/adr/0013`)
- `config/urls.py` — URL routing, with `set_theme`, which the theme picker posts to, and the examples page, which every environment routes; under `DEBUG` also the error page previews
- `config/settings/base.py` — django-tailwind-cli (`django_tailwind_cli`, `TAILWIND_CLI_USE_DAISY_UI` with the `tailwindcss-extra` release pinned in `TAILWIND_CLI_VERSION`, the source stylesheet named by `TAILWIND_CLI_SRC_CSS` outside `STATICFILES_DIRS`; these settings live in this module only, because the production image builds under the test settings, `docs/adr/0016`), nonce-based Content Security Policy (`SECURE_CSP`, Django's `ContentSecurityPolicyMiddleware`), the `TASKS` framework wiring (`django_tasks_db` app; immediate backend in local/test, database backend plus the `taskworker` process in production), `TEMPLATES` with Django's own loaders (`APP_DIRS`) and the theme context processor last, and `FORM_RENDERER = TemplatesSetting`, which sends every form through the project's templates under `templates/django/forms/`
- `config/asgi.py` — ASGI entry point served by Uvicorn (Gunicorn + Uvicorn worker in production); with `realtime=channels` it also routes websockets to `config/websocket.py`
- `<project_slug>/users/` — Custom user model (username or email-based auth via django-allauth); `User.get_absolute_url` says how a user is addressed and `User.display_name` how one is shown, and templates and views go through them instead of forking on `username_type` (`docs/adr/0003`); `users/tasks.py` holds the Django Tasks example (plus a Celery variant with `use_celery=y`)
- With `identity_provider` other than `none`, sign-in through Microsoft Entra ID or Google next to password login: `SOCIALACCOUNT_PROVIDERS` in `base.py` (Entra through the generic OpenID Connect provider keyed by `oid`, `docs/adr/0007`; the trust decisions in `docs/adr/0008`), the provider's origin in the policy's `form-action`, `users/checks.py` reporting empty credentials, `users/providers.py` (Entra only: the provider subclass the adapter hands out, refusing a token without a usable `oid`), `users/tests/social.py` driving allauth's callback with the token verification patched for `test_social_login.py` and `test_providers.py`, and the generated `docs/authentication.rst`
- `<project_slug>/styles/` — The source stylesheet (a term in `CONTEXT.md`): `main.css` imports Tailwind CSS and its typography plugin, enables daisyUI, names its sources itself (`source(none)` and `@source`), so the scan covers the package's templates and modules and is the same in an image, where `.gitignore` is left out, and holds the rules no class can say (htmx's `htmx-indicator`, which htmx may not inject under the policy); `theme.css` is the own theme, `brand`, every value daisyUI reads written out, the default look and the style example a developer edits, with daisyUI's `dark` answering a dark colour scheme. They sit outside the static directories, because a manifest storage cannot resolve `@import "tailwindcss"`. Neither may hold `{{`, `{%` or `{#`. The built stylesheet, `static/css/tailwind.css`, is never generated and never committed: the watcher (`manage.py tailwind watch`, the `tailwind` service of the local Compose file, its CLI in a named volume) rebuilds it, and the production image builds it in its build stage (`docs/adr/0016`)
- `<project_slug>/themes.py` — The themes a visitor may choose and the cookie that keeps the choice (`docs/adr/0017`): `THEMES`, the own theme and then daisyUI's 35 in the order `styles/main.css` enables them, a tuple so that the reader can read it (`docs/adr/0001`); `current_theme` and the `theme` context processor, which let only a cookie naming one of them reach `data-theme`; and `set_theme`, which the picker posts to through htmx: no content for a theme, since the checked `theme-controller` radio has restyled the page already, `HX-Refresh` for "system", a redirect back without htmx, 400 for an unknown name, and no transaction
- `<project_slug>/examples/` — The examples page (a term in `CONTEXT.md`), routed in every environment and linked from the navigation while its route exists, so deleting the package, `templates/examples/` and its line in `config/urls.py` removes it: `content.py` (the examples it names, `source`, which reads a template as written for those names only, and the sample tasks and tabs), `forms.py` (one widget of each kind, validated on the server; the filter), `views.py` (every view is `HtmxTemplateMixin` on `examples/index.html` naming a partial: the filtered and paged table, the form, the toggle, the lazy tabs, the dialog held open by `modal-open`, the out-of-band notices; without htmx each answers with the whole page or a redirect to it; no transaction, since the page is public and keeps nothing on the server beyond one cookie), and `tests/`, which run without database access except for the home page rendered under `tests/urls.py`, the project's URLs without the page. Not an installed app
- `<project_slug>/htmx.py` — `HtmxTemplateMixin` (renders `template.html#partial` for htmx requests, adds `Vary: HX-Request`) and `HtmxLoginRedirectMiddleware` (turns login redirects into `HX-Redirect` for htmx requests)
- `<project_slug>/sentry/` — With `use_sentry=y`, the app whose `ready()` initialises the Sentry SDK from the `SENTRY_*` settings that `production.py` defines and that install it (`docs/adr/0006`)
- `<project_slug>/metrics.py` and `config/gunicorn.py` — With `observability=prometheus`, the metrics of django-prometheus: the app and the middleware pair that wraps the chain, the instrumented database and cache backends and the `METRICS_TOKEN` setting in `base.py`, the endpoint routed in `config/urls.py`, and the guard, which takes a bearer credential and never a session, so what reads it is a machine (`docs/adr/0018`). With a provider the guard routes on the credential's unverified issuer: a calling service's token is verified and its registration must hold `identity.read_metrics` (403 without it), anything else is compared with `METRICS_TOKEN`, and neither falls back to the other (`docs/adr/0019`). Under Gunicorn each worker keeps its own registry, so `compose/production/django/start` exports and empties `PROMETHEUS_MULTIPROC_DIR` before Python starts and `config/gunicorn.py` reports an exited worker to the client, which retires that worker's `live` gauges and keeps everything else it recorded; one scrape then describes the container, and Prometheus scrapes every replica rather than the proxy in front of them. The local Compose file runs a receiver, `compose/local/prometheus/prometheus.yml`, and the generated `docs/observability.rst` carries the deployment's scrape configuration
- `<project_slug>/telemetry/` — With `observability=opentelemetry`, traces and metrics over OTLP: `configure.py` holds `configure(component)`, which installs a `TracerProvider` and a `MeterProvider` on the process, gives it a `service.instance.id` of its own (`<component>-<hostname>-<pid>`) and instruments Django, psycopg and redis, with Celery under `use_celery=y`; it starts nothing while `OTEL_EXPORTER_OTLP_ENDPOINT` is empty or the process has started already. `apps.py` calls it from `ready()` only where `DJANGO_TELEMETRY_COMPONENT` names the component, because `ready()` runs for every management command and, under Celery's prefork pool, before the fork (`docs/adr/0020`). The entry points are Gunicorn's `post_fork` in `config/gunicorn.py`, Celery's `worker_process_init` and `beat_init` in `config/celery_app.py`, and that variable, which `compose/local/django/start` and `compose/production/django/tasks/worker/start` export. Each process flushes where it can be reached on its way out: `telemetry/asgi.py` answers the server's lifespan shutdown and `config/asgi.py` wraps the application in it, because Gunicorn's uvicorn worker re-raises its signal before any exit hook or `atexit` runs; a Celery worker process flushes from `worker_process_shutdown`; everything else exits normally and the SDK's `atexit` hook does it. `shutdown` is bounded at `SHUTDOWN_TIMEOUT_MILLIS`, since the SDK's own timeouts are best-effort. `configure` also sets `OTEL_SEMCONV_STABILITY_OPT_IN` to `http,database` before it instruments, so the attribute and metric names are the stable ones (`http.request.method`, `http.server.request.duration`, `db.system.name`) rather than the older ones the instrumentations default to; a deployment overrides it from the environment. The `OTEL_*` settings sit in `base.py` with every default off, so a checkout, a command and the suite export nothing; the local Compose file runs a collector that prints what arrives (`compose/local/otel-collector/config.yml`), and the generated `docs/observability.rst` carries the deployment's collector configuration
- `<project_slug>/identity/` — With a provider and something that reads a calling service's token — `rest_api=Django Ninja`, or `observability=prometheus` — the app behind those services, and with Django Ninja the single-page application's login too (`docs/adr/0019`). The login side is Django Ninja's alone and goes without it, together with the policies below: `base.py` configures allauth's headless API (app client only, JWT strategy, HS256 with `DJANGO_HEADLESS_JWT_PRIVATE_KEY` drawn per environment by the secrets table, stateful validation, refresh rotation, `HEADLESS_FRONTEND_URLS` as the five-path contract with the SPA) and CORS for `DJANGO_FRONTEND_ORIGINS`; `identity/apps.py` refuses to start with an empty key or a non-positive lifetime (`validate_token_settings`, also run on the loaded production settings by `tests/test_production_settings.py`); `identity/checks.py` requires the frontend URL to be a configured origin, with `identity/frontend.py` normalising origins for it and for the account adapter's `is_safe_url`; the `revoke_jwt_sessions` command deletes the sessions behind app-issued tokens after a key rotation
- `<project_slug>/identity/` (services) — `identity/models.py` holds `ServiceRegistration` (admin with the subject read-only after creation; `has_perm` checks the enabled flag and the full `app_label.codename`); `identity/verification.py` verifies provider-issued tokens with PyJWT (RS256 fixed; Entra's tenant, `idtyp`, role and `oid`, or Google's issuer allowlist, audience and `sub`; `DiscoveredKeys` discovers at first use and retries a failed discovery; rejections logged by fixed branch and reason codes, expiry at info, the rest at warning, identical warnings collapsed per minute) and holds `unverified_issuer`, which every caller that routes by the issuer reads a token with; `identity/auth.py` holds the Ninja policies (`user_auth`, set globally by `config/api.py`: an app-issued JWT whenever an `Authorization` header is present, else the session with its CSRF check; `service_auth`; `either_auth` routed by the unverified issuer); `identity/permissions.py` holds `require_permission`, the 403 of a route under `either_auth`; `identity/api.py` serves `/api/principal/`; `identity/tests/headless.py` drives the app client and `identity/tests/services.py` mints RS256-signed service tokens for the tests; `identity/tests/test_verification.py` calls the verifier rather than a caller of it, so it runs whichever caller was generated. With `observability=prometheus` the registration also carries the `read_metrics` permission (migration `0002`), which `<project_slug>/metrics.py` requires
- `<project_slug>/tests/` — Project-level tests that belong to no single app: the Content Security Policy, the htmx helpers, the stylesheet built into a temporary directory and the static collection under a manifest storage, with the rules the templates rely on looked up in the built file (`test_staticfiles.py`, WhiteNoise's when generated with it; its first run downloads the Tailwind CLI), Django's form renderer on the project's field, widget and error-list templates, the admin included (`test_forms.py` with `forms.py`), allauth's elements from a fixture template under `tests/templates/` and its pages (`test_allauth.py`), the starter pages and the navigation (`test_pages.py`), the theme picker, its cookie and the parity of `THEMES` with the source stylesheet, the posts without database access (`test_themes.py`), the error pages rendered with database access blocked (`test_error_pages.py`), with `realtime=channels` the websocket consumer and with `use_sentry=y` the Sentry wiring; `markup.py` parses rendered markup for them
- `tests/` — Tests of the root-level files, pruned together with `.envs`: the dotenv merge script and the production settings loaded under the declared environment
- `.envs/` and `docker-compose.*.yml` — The environments (the term is in `CONTEXT.md`): `local` on the developer's machine, and `dev`, `test` and `production`, in the order a change is promoted through them. A deployed environment is configuration alone — its own env files, Compose file, hosts, secrets and Traefik routers — over the one production settings module and the one set of production images (`docs/adr/0013`); in the template its env files, its Compose file and its routers are rendered from the shared source (`docs/adr/0023`)
- `.env.example` — No env file is in version control (`.gitignore` ignores `.env` and `.envs/*`, whatever the answers), so this committed example is what a checkout reads the deployment's variables from: the production env files merged with every drawn value left unset, written by `write_example_dotenv` before `fill_secrets`, and loaded by the generated `tests/test_production_settings.py` (`docs/adr/0014`)
- `compose/` — Docker configs: `compose/local/` for the developer's machine and `compose/production/` for every deployed environment. Traefik's configuration is split there: `traefik.yml` (static, pointing at the dynamic directory), `dynamic/shared.yml` (the services and middlewares every environment shares) and `dynamic/{dev,test,production}.yml` (each environment's routers, stubs of the shared source in the template), the last selected by the image's `ENVIRONMENT` build argument
- `AGENTS.md` — The agent guide (the term is in `CONTEXT.md`), rendered for every project and placed by the hook under the name the `coding_agent` answer names: `CLAUDE.md`, `AGENTS.md` or `.github/copilot-instructions.md`, or deleted with `none` (`docs/adr/0015`). It records the answers the project was generated from, its commands, its layout and its conventions, all of it forked on the answers, so a claim it makes is a claim about the tree that exists
- `pyproject.toml` — The pinned dependencies, templated into `[project.dependencies]` and the `dev` dependency group; generation writes no `uv.lock`, the developer's first `uv sync` does
- `<project_slug>/templates/` — Pages written with daisyUI's component classes and Tailwind's utilities, with no component layer of the project's own: `base.html` loads the built stylesheet through `{% tailwind_css %}` and nothing else, writes the chosen theme as `data-theme` (never an empty one: daisyUI's rule for a dark colour scheme applies to a root without the attribute), marks `<main>` with `hx-history-elt` so htmx's history never restores a theme picker of the past, and renders the messages partial, one daisyUI alert per message, dismissed by a CSS-only checkbox (`has-[:checked]:hidden`); `partials/navigation.html` is the navbar, its page links a partial rendered twice (a dropdown that opens on focus for small screens, a horizontal menu for large ones), with the theme picker, a form of `theme-controller` radios posted through htmx on change and by a `noscript` button without it; `django/forms/field.html`, the widget templates beside it and `errors/list/ul.html` give every form Django renders its classes and keep Django's associations (label, `aria-describedby`, `aria-invalid`, which is also what colours an invalid control), with `widgets/attrs_without_class.html` instead of an override of Django's `attrs.html`, which the admin's widgets include; `templates/allauth/` overrides every allauth element and both layouts, since Tailwind's preflight leaves a bare element without a look; `templates/examples/` holds the examples page and one small template per example, which the page renders and shows as written, and `base.html` provides `<div id="modal">` for a dialog an htmx request fetches. htmx is loaded through django-htmx's `{% htmx_script %}` (with the `hx-ws` extension when `realtime=channels`). htmx fragments are `{% partialdef %}` partials inside the page template, selected with `htmx_partial` on the view. No Node.js, no CDN and no JavaScript of the project's own; the one build step is the Tailwind CLI's.

## Conventions

- **Python 3.12–3.14** supported (`requires-python = ">=3.12"`); 3.14 is the default via `.python-version` and the Docker images
- **No inline code in templates**: the CSP has no `unsafe-inline`, so no inline `<script>`/`<style>`, `style=` attributes, `on*=` or `hx-on*` handlers (enforced by `test_no_inline_code_in_templates`); a necessary inline script takes `nonce="{{ csp_nonce }}"`; an htmx fragment holds no `<script>`, `<style>` or `<link>` at all (the generated view tests assert it on the fragments they receive)
- **Jinja in the template sources**: templated Python, templates, stylesheets, the generated guide and the shared source avoid `{{`, `{%` and `{#` outside cookiecutter's own syntax and `{% raw %}` blocks, because Cookiecutter renders every file
- **No JavaScript of the project's own**: what involves the server is an htmx request; what does not is one of daisyUI's CSS-only mechanisms (a dropdown that opens on focus, `collapse` on a `<details>`, checkbox- and radio-driven parts). `test_tailwind_and_daisyui` allows no `.js` file in a generated project, and `allowEval` keeps `hx-on*` off
- **Class names are written whole**: Tailwind generates a rule only for a class name it finds written out in a scanned file, the package's templates and Python modules, so a template chooses between whole names and never assembles one (`test_class_names_are_written_whole`, which does not prove that every class used is in the built stylesheet: a missing style shows in a browser, not in the suite)
- **No trace of a removed frontend**: `test_no_trace_of_a_removed_frontend` scans every generated file of every combination for the names, syntax, settings and files of the frontends this template removed and for a Node.js toolchain's tokens, with the drawn secrets masked first; generated prose therefore avoids those words
- **Line length**: 119 characters for ruff in this repository; generated projects keep ruff's default of 88 (their djlint allows 119), so keep template Python within 88 columns
- **Ruff** for linting/formatting; config in `pyproject.toml` under `[tool.ruff]`
- **djLint** runs on the generated projects, not on the template sources, with the generated `[tool.djlint]` (`profile = "django"`; `custom_blocks` names allauth's `element` and `slot` and Django's `partialdef`): `test_djlint_lint_passes` lints every combination in the default suite, and `test_djlint_check_passes` checks the formatting with `AUTOFIXABLE_STYLES=1`. This repository has no djlint config or hook of its own, so write template HTML the way djlint leaves the rendered output
- Template files under `{{cookiecutter.project_slug}}/` are excluded from ruff (not parseable Python)
- **Settings templates** render each setting from one block: the answers a module forks on are bound to names at its top, a choice from a list (mail service, mail catcher) is a row in a table there, and the block forks on each answer where it decides something (`docs/adr/0005`)
- **Calendar versioning**: `YYYY.MM.DD`

## Adding a New Template Option

1. Declare it in `cookiecutter.json`: a list of choices makes a list option, a `"y"`/`"n"` default a flag option, any other text a free-text option. Add it to `KINDS` in `tests/test_options.py`. Nothing else registers it: the pre-generation hook lowercases and validates every flag and checks every free-text answer for control characters, and the generation tests bake every choice
2. Add validation specific to the option in `hooks/pre_gen_project.py` if needed
3. In `hooks/post_gen_project.py`: add a removal rule to `REMOVALS` for the files the option makes unnecessary, with the expected removals in `tests/test_hooks.py`; add a cleanup step to `prune` only when a deletion depends on what else is left in the generated tree, as the Channels cleanup does; a new `!!!SET NAME!!!` placeholder is a row in `SECRETS` (`per_deployed_environment(...)` if each deployed environment draws it for itself), with its site added to `PLACEHOLDER_SITES` in `tests/test_hooks.py` (`DEPLOYED_DJANGO_SITES` or `POSTGRES_SITES` for the deployed env files, stated once); put other content modifications in `main`, and a line the generated project must ignore in the template's own `.gitignore` rather than appending it from the hook
4. Use Jinja2 conditionals in template files: `{% if cookiecutter.option == 'y' %}`, and fork any mention of a file your rule removes on the same answer, since `test_no_file_cites_a_path_its_answers_removed` fails for a generated file that names a path its answers pruned; a deployment variable goes into `templates/deployed/django.env` (or `postgres.env`), a service or volume into `templates/deployed/compose.yml` and a router into `templates/deployed/routers.yml`, once, never into a deployed environment's stub; read a derived answer (`cookiecutter.headless`, `cookiecutter.service_tokens`) rather than re-deriving it from the answers, which `test_no_template_re_derives_a_derived_answer` refuses, and make a new condition a derived answer in `derived_answers` only when it combines two or more answers and is read by files of more than one kind, the hook among them (`docs/adr/0022`); write a free-text answer through the escaping filter of the file's syntax (`| string_escape`, or `| e` in HTML; see Escaping in `CONTEXT.md`). An option that adds files, commands or conventions to the generated project gets an arm in the agent guide, `{{cookiecutter.project_slug}}/AGENTS.md`, whose tables the generation tests check against the tree
5. Add a row to `PAIRED_COMBINATIONS` in `tests/test_cookiecutter_generation.py` when `test_every_removable_path_is_baked` asks for it: a path of your removal rule that only survives together with another answer fails there, with the row to write. Add the answers to an existing row of the `docker` or `bare` job in `.github/workflows/ci.yml` when `test_every_removable_path_is_generated_by_some_ci_row` names a path (a new job only if widening a row would hide which answer a failure belongs to; an exemption only for a path nothing the integration scripts run reads). A fork inside a file that some row keeps anyway is not checked (`docs/adr/0021`), so add its row by hand when the arm needs a second answer to be reached — a guide arm needs `coding_agent` answered with an agent, which the rows there already pair with the answers the guide forks on; an option rejected in some combination goes into `UNSUPPORTED_COMBINATIONS`
6. Document it: an entry in `docs/1-getting-started/project-generation-options.rst`, in declaration order, with a list option's choices as an enumerated list whose items start with the answer as typed; and its prompt in the README's example session. `tests/test_options.py` checks both against the catalogue
